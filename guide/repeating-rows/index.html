Forms that repeat a set of fields

Add-a-participant, add-a-line, add-another-dependant. How Grispy saves rows, and the one question it asks before it would drop any.

Some forms let you add the same set of fields over and over — a name and date of birth per traveller, a description and amount per line. Grispy recognises those as rows and saves each one separately, so a four-participant booking comes back as four participants rather than one.

How rows appear

In the save list and the preset preview, a field inside a repeating group carries its row number:

Surname (row 1) · Surname (row 2) · Surname (row 3)

Rows are numbered from the top of the page as it stands when you save. A field that is not inside a repeating group has no row number at all.

The problem this creates, and the question that solves it

Forms like this usually start with one row and grow as you press "Add another". So the page you return to is very often showing fewer rows than you saved — and a save writes what is on the page.

Left alone, that would silently destroy the rows you could not see. Grispy will not do that. When a save would drop rows, it stops and asks:

This page shows 2 of 5 saved rows The headline. What the page is showing, against what is stored.
Saving just these 2 discards the other 3. There is no undo. What the destructive answer costs.
Keep all 5 Preselected. The rows on screen are updated, and the ones that are not rendered survive untouched.
Save just these 2 A deliberate replacement: the stored rows become exactly what is on screen.

When the page is showing no rows of a group you saved, the wording changes to match — This page shows none of the 5 saved rows, with Save without them as the destructive answer.

The question appears only when there is something to lose. An ordinary save on a page showing everything you saved never sees it.

Filling a form with rows

Press Fill and the answers go into the rows the page is currently rendering. When some rows are missing, the message says so:

Filled 8 of 20 fields. · 2 of 5 saved rows present

The row clause comes after a middot and is separate from the field counts — it is not a third sentence, and it is not derived from the fields. It counts rows; the numbers before it count fields. More on the field counts.

Grispy does not press "Add another" for you. If the page is showing two rows and you saved five, three rows have nowhere to go — they are reported as not filled, and you add the rows by hand and fill again. Adding rows for you needs Grispy to find each form's own Add button, which has no reliable name to find it by; it is not built.

The routine that works

  1. Press "Add another" until the page shows as many rows as you saved. The popup tells you the number: 2 of 5 saved rows present.
  2. Then press Fill. With the rows in place, every one of them fills.
  3. If you fill first, nothing is lost — add the rows and fill again. The second fill overwrites the first harmlessly.

Known limits

Three, and the first is the one that can actually cost you something.

Rows are matched by position, not identity

Grispy knows a row by where it sits, so it cannot tell a page showing your 3rd and 4th saved rows from one showing your 1st and 2nd. If you delete a row from the middle of a list and then save with "Keep all", the rows on screen can be merged over the wrong stored ones. When you have deleted a row, the safe answer is the other one: get every row you want on screen, then choose Save just these, which replaces the stored set outright.

Rows built from checkboxes or radio buttons are not recognised

Where each repeating row is a set of checkboxes or radio buttons rather than text fields, Grispy does not see a repeating group at all. Those fields are saved and filled as ordinary loose fields, which on a multi-row form will not do what you want.

A row you cannot see is a row Grispy will not guess at

Everything above follows one rule: Grispy acts on what the page is showing. It does not invent rows, and it will not quietly drop the ones it cannot see.
